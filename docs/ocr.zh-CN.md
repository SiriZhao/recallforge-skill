# 本地 OCR 验证

RecallForge 的默认路径是原生提取 → 宿主视觉 → 明确 unresolved。本地 OCR 只是可选后备，不是核心要求。

## 已验证引擎（参考运行）

参考环境：Windows 11、Python 3.14.3、Intel64 Family 6 Model 197、仅 CPU。十个自制 fixture：英文清晰扫描、中文清晰扫描、中英混排、低分辨率、倾斜、双栏、试卷、公式上下文、表格、批注覆盖。

| 指标 | Tesseract 5.5.0 | RapidOCR 1.2.3（ONNX CPU） |
|---|---|---|
| 平均 CER | 0.2578 | 0.2492 |
| 中位 CER | 0.2630 | 0.1503 |
| 平均 WER（适用时） | 0.1956 | 0.1490 |
| 完成 fixture | 10/10 | 10/10 |
| 总耗时 | 5.15 秒 | 51.59 秒 |
| 页/秒 | 1.94 | 0.19 |
| 冷启动 | 未单独分离（首次约 0.4–0.7 秒） | 0.78 秒 |
| 安装体积 | 系统二进制约 90 MB + 语言数据 | Python venv 内约 190 MB |
| 中文清晰 CER | 0.2759 | 0.1379 |
| 中英混排 CER | 0.2979 | 0.6383 |
| 试卷 CER | 0.3810 | 0.1111 |
| 公式上下文 CER | 0.5417 | 0.8125 |
| 表格 CER | 0.2500 | 0.0000 |
| 批注覆盖 CER | 0.1600 | 0.1200 |

完整机器可读结果：[benchmarks/results/ocr-windows-reference.json](../benchmarks/results/ocr-windows-reference.json)。

## 这些数字意味着什么

- 两个引擎都能恢复清晰印刷文字，但都不能被当作已验证理解。公式符号和中英混排数学标点尤其弱，仍需要宿主视觉或用户核对。
- RapidOCR 在这组 fixture 中更擅长清晰中文、表格、试卷和批注，但 CPU 上明显更慢。
- Tesseract 更轻更快，本次混排和公式上下文文字更强，但中文质量弱于 RapidOCR。
- 双栏阅读顺序两个引擎都不能可靠恢复；这是布局问题，不是字符识别问题。
- `B?` 之类的批注会被识别为独立文字。RecallForge 仍会把所有手写内容标记为用户/未知批注，绝不自动当作印刷标准答案。

## 推荐处理矩阵

| 资料 | 推荐路径 |
|---|---|
| 数字 PPTX | 原生 + 必要时宿主视觉 |
| 数字 PDF | 原生 + 选择性宿主视觉 |
| 清晰扫描件 | 宿主视觉优先 |
| 大批量清晰扫描 | 可选本地 OCR + 宿主视觉复核 |
| 公式密集扫描 | 宿主视觉优先；本地 OCR 只用于周围正文 |
| 图示密集资料 | 宿主视觉优先 |
| 往年试卷 | 原生/OCR + 宿主视觉结构恢复 |

## 结论

本地 OCR 仍是可选实验后备，不是中文资料的推荐路径，也绝不能单独用于公式、图示、表格或试卷结构。`OCR_QUALITY` 不构成发布阻塞，因为产品推荐路径是宿主视觉；以上数据作为真实证据公开，而不是作为支持质量承诺。
